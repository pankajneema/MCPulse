# Security — development build

Anyone controlling an authorized approval channel can authorize host actions. Treat the installation secret, bot/app tokens, hook headers, signed action links, and the allowlisted accounts as credentials. This is a trusted single-user local application; it has not passed an external security review.

The daemon API binds only to 127.0.0.1, requires a constant-time HMAC-derived key check, rejects browser origins, and bounds body/concurrent request sizes. **Never expose port 7717.** The optional confirmation/webhook listener is separate, defaults to 127.0.0.1:7718, and must sit behind your own TLS proxy/tunnel. It does not accept the daemon API's administrative routes.

The local dashboard is a separate `/ui` route on the daemon listener. `ui` obtains a 60-second, single-use login ticket through the authenticated API; the installation secret is never placed in a browser URL. Browser sessions are in-memory, bounded, expire after eight hours, and use HttpOnly/SameSite=Strict cookies scoped to `/ui`. Lock removes the session; restart invalidates all sessions. Cookie authentication cannot access the API. Every UI mutation requires a session-bound CSRF token; supplied foreign or null Origins are rejected, as are non-loopback Host values. Some clients omit Origin, so a missing header still requires the authenticated cookie and CSRF token. High-risk dashboard approvals additionally require a PIN and an explicit review checkbox, with failed PIN attempts limited per request. GET never approves. The dashboard is deliberately loopback HTTP, without a Secure cookie; never proxy or expose this listener. Other local applications and browser extensions remain within the trusted-host threat model.

The confirmation pages and dashboard use `Referrer-Policy: same-origin`: URLs are not sent to other origins, and native form posts retain their Origin. A `no-referrer` policy can cause a null Origin on form posts ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin)). No third-party scripts, fonts, analytics, or assets are loaded by the UI.

Telegram and Slack validate sender identity, conversation, and the original card message. WhatsApp verifies the raw Meta HMAC signature, business phone id, sender, freshness and replay ids. High-risk button grants require a fresh second confirmation. Typed/web high-risk approvals require a configured PIN; attempts are throttled. A second tap is not a second factor against a compromised chat account. A low/medium-risk action link is a bearer capability; possession is authority until it expires or is consumed. GET never approves; POST requires the matching confirmation token. No link grants broad account or daemon access.

Requests resolve once under a lock and audit/database transaction. Expired/closed replies cannot grant. Edits are checked again by policy. Remembered grants match the entire original tool/input and project, and are unavailable for high-risk or disguised/compound inputs. Trusted-project rules require explicit opt-in. Regex matching has a subprocess time budget. Built-in command patterns are heuristic, not a shell sandbox. High-risk commands never auto-allow even under a broad configured allow rule.

Masking covers common secret patterns, and altered/truncated request fields disable remote grants. Redaction cannot guarantee detection of arbitrary or encoded secrets. Context processing is limited to bounded transcript tails beneath ~/.claude; raw transcript files are not uploaded. Cards do send request text, project/session information, and sanitized context directly to configured providers.

POSIX state/config/token files use mode 0600 within a 0700 directory. OS keychain storage and Windows ACL hardening are not implemented. Pending requests retain the full original payload in private SQLite for recovery. On completion, the raw payload and detailed card contents are logically cleared; only request ID, sanitized project, agent and session metadata remain in the card for dashboard receipts. This metadata and the response are kept for up to 24 hours for status checks and hook retry. Responses may contain user answers or edited tool input. Database pages/WAL/backups can retain deleted bytes. Audit stores only id/state/source/time; default retention is 30 days. Protect the entire state directory as sensitive data.

A daemon/network failure returns control to Claude's normal permission flow; it is not automatic approval. The default command hook retries temporary daemon outages for up to 30 seconds. Unreachable clients cannot cancel persisted requests until connectivity returns; original TTL bounds their lifetime. A request may have already been decided when a response is lost, so the client retries the same id without creating another grant.

Tests cover authentication, malformed inputs, replay/races, expiry, private file modes, settings restoration, MCP cancellation, request recovery, PIN checks, signed links, and mocked channel identities. Live provider tests, full secret/unicode corpora, cross-platform service/reboot tests, penetration testing, release signing, and the hosted/team security model remain outstanding. Do not label this build production-ready.

No public security contact or repository remote has been configured. Report vulnerabilities privately to the project owner through an established channel; never attach tokens, private configuration, or raw command payloads to public reports.
